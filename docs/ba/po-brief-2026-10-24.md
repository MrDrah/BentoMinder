Use our existing Agentic Engineering Boilerplate and coordinate its BA, Designer, Developer, QA, Verifier and Metrics agents as appropriate. ## 2. Product vision
**BentoMinder — おべんとう、忘れない。** A simple family application that helps Japanese parents remember homemade bento days and decide what to prepare.

**The real-world problem.** Our daughter's kindergarten publishes its monthly lunch menu online as a public PDF. Parents normally prepare homemade bentos but can alternatively reserve the school's lunch on the morning of the relevant day. In our family, we usually choose school lunch. However, when the published meal is something our daughter probably won't enjoy, my wife may decide to prepare a homemade bento. Two problems occur:
1. I sometimes forget which days my wife intends to prepare a homemade bento.
2. Choosing what to prepare requires additional planning and effort.

BentoMinder should solve these problems with minimal interaction.

**Core experience**
1. Import the kindergarten's monthly lunch PDF.
2. Assess which meals the child is less likely to enjoy.
3. Display those days clearly in a calendar.
4. Tap a day and receive three suitable homemade bento suggestions.
5. Choose a bento and lock the decision for that day.
6. Receive reminders before planned homemade bento days.

The objective is not to replace the school's reservation system. The objective is to help the family remember the plan and prepare accordingly.

## 3. Target audience and language
Primary users are Japanese parents with children attending kindergarten or elementary school. Japanese is the default application language. Include an easily accessible 日本語 / EN toggle. All visible UI strings must support localization. Prefer natural Japanese phrasing over literal translations from English. Use Japanese date formats, the Asia/Tokyo timezone and familiar mobile calendar conventions. The application should be understandable by a busy parent in a few seconds.

## 4. MVP user experience
Prioritize simplicity over feature quantity.

**First launch.** If no profile or menu exists, guide the parent through a short onboarding process:
1. Create a child profile.
2. Enter the public URL of the school's monthly lunch PDF, or upload the PDF.
3. Import and review the extracted school menu.
4. Display the main calendar.

**Subsequent launches.** Open directly to the calendar, focused on the current month and upcoming bento decisions. The primary interface should contain:
- A compact summary of upcoming homemade bento days.
- A monthly calendar.
- Clearly highlighted low-preference lunch days.
- Confirmed homemade bento plans.
- A way to access recipes and settings.

Avoid unnecessary dashboards, statistics and complex navigation.

## 5. Child profile
Create one child profile for the MVP. Collect:
- Optional nickname.
- Age or age range.
- Favourite food categories and ingredients.
- Disliked categories and ingredients.
- Dietary preferences.
- Known allergies or explicit unknown status.
- Favourite creative themes, such as dinosaurs, animals, stars, vehicles or flowers.

Use structured controls wherever practical. An optional free-text field may allow parents to describe additional preferences. Do not collect exact birthdates, height, weight, gender or other unnecessary information. Store data locally for the MVP using a versioned schema. Support editing, exporting and deleting the profile. Do not send identifying child information to external AI providers.

## 6. School lunch menu import
The school publishes a monthly menu as a public PDF accessible through a URL.

**Primary input.** The parent supplies the public PDF URL during onboarding. Store the source URL so it can be reused for a later import when appropriate.

**Fallback.** Allow manual PDF upload when automatic retrieval fails. Do not assume arbitrary external URLs are accessible from browser JavaScript.

**AI extraction.** Use an AI model to interpret the Japanese monthly school menu. Convert the document into structured JSON containing: date; menu item names; listed ingredients, when available; allergen declarations, when available; special notes; days without school lunch; source information; verification and uncertainty status.

Do not invent missing items or infer that an unlisted allergen is absent. After extraction, show an editable review screen so the parent can confirm the imported menu. Store the confirmed data locally. Importing a menu should normally require only one AI processing operation per month, with retries only when necessary.

**Refresh behavior.** Allow the parent to replace the monthly menu. Warn when the currently displayed menu is outdated. Keep existing homemade bento decisions when refreshing menu data, unless the parent explicitly changes them.

## 7. AI integration
The MVP should use a real AI model for monthly school-menu interpretation.

**Preferred provider.** Investigate the free tier of the Google Gemini Developer API. Select a currently available model with Japanese-language, PDF and structured-output capabilities. Do not assume a particular model is free without checking its current eligibility and limits. The primary objective is accurate structured extraction, not creative generation.

**Security and architecture**
- Never expose API credentials in web or Android client code.
- Use a suitable secure server-side adapter or a supported protected AI integration.
- During local development, a local backend proxy is acceptable.
- Never commit API keys.
- Do not activate paid API usage without product-owner approval.
- Validate returned JSON against a schema.
- Handle malformed output, unavailable services and rate limits.
- Maintain test fixtures so the app can be developed without live AI access.

Use only the public lunch document as model input unless the parent explicitly approves additional data transfer. Explain relevant free-tier privacy limitations before enabling the integration.

**AI responsibility boundaries.** The LLM interprets the school menu. After that, application logic should normally operate without calling AI again. Preference scoring, reminders and recipe matching should be deterministic, explainable and testable. No unnecessary runtime AI agents.

## 8. School lunch preference assessment
Compare the confirmed monthly lunch menu with the child's preferences. Identify dates with meals the child may be less likely to enjoy. Use simple states: likely enjoyable; mixed or uncertain; low preference; not assessed; no school lunch.

Every assessment should have a short explanation. Example: 「水曜日の給食には、苦手な食材が2つ含まれています。」

Do not label a meal objectively unhealthy, bad or unsuitable merely because it contains disliked ingredients. Allow parents to override assessments manually. Manual overrides must persist until changed. The recommendation system must never automatically book or cancel a school meal.

## 9. Calendar and meal decisions
The calendar is the application's primary screen. For every school day, maintain two separate pieces of information:
1. Preference assessment: whether the school lunch seems appealing.
2. Family decision: school lunch or homemade bento.

A low-preference assessment does not automatically create a homemade bento plan.

**Family decision states:** school lunch planned (default); homemade bento planned; decision not yet confirmed, where applicable; no school lunch.

Selecting a homemade bento should open the bento recommendation experience. Once the parent chooses and confirms a recipe, mark the day as planned and display the selected bento's name. Allow parents to edit, replace or cancel plans. Make the difference between suggested and confirmed homemade bento days visually unmistakable.

**School lunch reservations.** School lunch reservation remains an external process managed by the parent. The app must not claim that changing the calendar has made a school reservation. Optionally allow a parent to mark the external school lunch reservation as completed. Provide a clear morning summary of today's meal decision.

## 10. Bento recommendations
When the parent selects a day for homemade bento, propose three recipes. Use a curated and verified recipe library. Start with approximately 15–20 realistic bentos suitable for young children, including Japanese and Western-inspired options. Each recipe should contain: name in Japanese and English where appropriate; ingredients and quantities; preparation instructions; approximate preparation time; storage and food-handling guidance where supported; dietary and allergen metadata; source reference; optional creative theme.

Rank recipes based on food preferences, dislikes, variety and preparation effort. Known allergens and dietary exclusions must be handled using deterministic rules. Unknown ingredient or allergen information must be explicitly flagged, and the app must never guarantee allergy safety. When a parent selects a recipe, store it against the calendar date. Provide a simple recipe detail screen and the ability to change the selected recipe. For the MVP, do not generate a new recipe using AI on every request.

## 11. Reminder system
Notifications are a core feature of BentoMinder.

**Weekly reminder.** Default: Sunday at 14:00 JST. Summarize the following week's low-preference school lunch days and any confirmed homemade bento plans. Offer quick access to planning an unconfirmed day.

**Day-before reminder.** Default: 17:30 JST, before the parent normally prepares dinner. Trigger for confirmed homemade bento days. Example: 「明日は手作りお弁当の日！レシピを確認しましょう。」 Open the selected recipe or calendar day when tapped.

**Same-day overview.** Show a simple current-day status: school lunch planned; homemade bento planned; no school lunch. If applicable, remind the parent that actual school lunch reservations are completed outside BentoMinder.

**Notification implementation.** Design a notification adapter supporting in-app reminders for the web version and scheduled native local notifications for the Android version. The browser version must not falsely promise reliable background notifications while closed. For Android, evaluate Capacitor Local Notifications. Notifications should be rescheduled or cancelled when calendar decisions change. Handle permission denial, timezone changes, duplicate notifications and expired reminders. Notification times should be configurable.

## 12. Browser and Android strategy
Build the application web-first using the framework's existing React/TypeScript stack. The web application must run locally and be testable with Playwright. Keep the architecture compatible with packaging as an Android application using Capacitor. The initial delivery plan should include:
1. Working mobile-responsive browser MVP.
2. Android build feasibility assessment.
3. Android test build with scheduled local notifications after the web functionality is stable.

Do not require Google Play publication for the initial experiment. Avoid rewriting the application separately in Kotlin. If native Android integration introduces significant complexity, document it and present options before proceeding.

## 13. Family sharing
The MVP will initially have one local child profile and locally stored plans. Recognize that data stored on one device is not automatically visible on another device. Provide a simple sharing action for the upcoming weekly bento plan using the operating system's share interface or copied text. Shared summaries must not expose unnecessary child profile data. Do not pretend that this feature provides automatic two-device synchronization. Future versions may introduce synchronized family planning, with appropriate authentication and access control. Document this as a known MVP limitation.

## 14. Visual design
The visual direction should be inspired by the gentle, playful French children's fashion aesthetic associated with Petit Bateau. Use an original visual identity rather than copying its branding. Keywords: soft and warm; playful but practical; clean and uncluttered; family-friendly; Japanese-first.

Consider cream-white backgrounds, navy typography, soft red accents and restrained decorative stripes. Use clear calendar indicators and large touch-friendly controls. Do not allow decorative styling to make the application harder to understand. Prioritize information hierarchy: What day? School lunch or homemade bento? What recipe? Present a design preview to the product owner before full implementation.

## 15. Debug tools
Include an unobtrusive development-only control panel. It should allow: simulating dates and times; triggering weekly reminders; triggering day-before reminders; loading a sample child profile; loading a sample Japanese monthly menu; testing AI extraction failures; clearing local test data; inspecting locally stored meal decisions. Keep debugging controls out of the normal production experience.

## 16. Engineering and QA
Use the existing boilerplate's engineering procedures, handoff gates, documentation and test strategy. Pay particular attention to: Japanese-language PDF extraction accuracy; school menu date mapping; preference scoring reproducibility; manual override persistence; meal-plan state transitions; allergies and unknown ingredients; recipe selection and editing; notification scheduling and cancellation; month boundaries and Japanese timezone behavior; local data persistence; Japanese/English switching; Android notification permissions; AI service unavailability; browser and Android consistency.

Test the main user journey end-to-end: Import PDF → confirm menu → identify low-preference day → choose homemade bento → select recipe → save plan → verify calendar → trigger reminder → reopen recipe.

Create realistic Japanese monthly menu fixtures for deterministic testing. Keep live AI evaluations separate from mocked tests.

## 17. Boilerplate evaluation and milestone evidence
This is the second application created using our reusable engineering framework. Use the existing Metrics & Evidence capability, if available. Record: functional success; human interventions; QA effectiveness; development costs; recovery and reliability; delivery results.

Generate a milestone evidence package after completion of the MVP. Do not modify the boilerplate to hide weaknesses discovered during this application. Document reusable framework lessons separately from BentoMinder-specific issues.

## 18. Execution instructions
Begin with the project kick-off. Delegate requirements analysis, architecture review and UI design according to the boilerplate. Present the product owner with:
1. Confirmed MVP scope and user journeys.
2. Proposed system architecture.
3. Free AI provider recommendation and secure integration plan.
4. Browser-to-Android implementation strategy.
5. Notification limitations and how they will be addressed.
6. Significant technical risks or product decisions.

Get approval for major architecture choices before full implementation. Once approved, implement in incremental milestones with independent QA. Do not push, deploy or use paid services without approval.

**Success criterion:** A Japanese parent can import a monthly kindergarten lunch PDF, identify potentially unpopular meals, plan and confirm homemade bento days, choose a suitable recipe, and reliably review or receive reminders through the supported application environment. The finished application should be extremely simple to operate, even if the engineering behind it is sophisticated.
